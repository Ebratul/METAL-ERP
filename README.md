# Metal ERP

> Enterprise resource planning for metal garments-accessories manufacturing — 75 core modules, 1,809 workspaces, one prerendered Next.js application.

Metal ERP is the front-end system of record for a metal accessories factory: buttons, rivets, snaps, sliders, eyelets, buckles and metal labels sold to global apparel brands. It covers the full commercial and shop-floor lifecycle — inquiry → quotation → proforma invoice → sales order → planning → production → plating → QC → packing → export → collection — plus the HR, finance, asset and governance functions around it.

Built by **Smart Global IT** (Chittagong, Bangladesh).

## Status: what this build is

**This is a complete front end with no backend.** Everything renders, navigates, filters, sorts, charts, validates and persists — but it does so entirely in the browser. Read this before wiring it to anything real:

| Concern | How it works today | What production needs |
|---|---|---|
| **Identity** | A `metal-erp-session` cookie set by the login screen against a hard-coded demo account ([`src/lib/org.ts`](src/lib/org.ts)) | A real IdP, signed `httpOnly` server sessions |
| **Authorization** | None — [`src/proxy.ts`](src/proxy.ts) is a *routing* gate, not a permission boundary | Server-enforced RBAC per module/record |
| **Data** | Deterministically generated from seeds; user edits persist to `localStorage` per workspace | A database and API layer |
| **Rendering** | 1,892 statically prerendered pages | Dynamic rendering for live data |
| **CSP** | `script-src` carries `'unsafe-inline'` because static HTML cannot take a nonce (documented in [`next.config.ts`](next.config.ts#L3-L20)) | Per-request nonce once pages go dynamic |

Nothing behind the login gate is secret, so the demo credentials are pre-filled on the sign-in form by design.

## Quick start

```bash
# Node.js 20.9+ required (Next.js 16)
npm install
npm run dev
```

Open <http://localhost:3000>. Every route is gated, so you land on `/login`:

| Field | Value |
|---|---|
| Email | `admin@smartglobalit.net` |
| Password | `admin123` |

Both are pre-filled. Signing in redirects to `/dashboard` (the CEO Command Center), or back to whatever page you originally requested via `?next=`.

No environment variables are required — `.env` is intentionally empty. The app makes zero cross-origin requests.

### Production build

```bash
npm run build     # ~1,892 static pages
npm start         # serves the production build on :3000
```

## Architecture

### Route map

```
/                                   → redirects into the command centre
/login                              → session gate (dynamic)
/dashboard                          → CEO Command Center
/modules                            → directory of all 75 modules
/m/[module]                         → module landing: submodule grid + module KPIs
/m/[module]/[submodule]             → the workspace itself
/_not-found                         → unknown module or submodule slug
```

Both dynamic segments are fully enumerated by `generateStaticParams()` and validated by `parseSlug()` before lookup — an unknown or malformed slug 404s rather than being escaped and rendered.

### The three rendering layers

[`ModuleWorkspace`](src/components/workspace/module-workspace.tsx) resolves every submodule route through three layers, most specific first:

```
                    ┌──────────────────────────────────────────┐
  /m/a/b  ───────►  │ 1. Flagship?  hand-built surface         │  5 routes
                    │    src/components/workspace/flagship/    │
                    ├──────────────────────────────────────────┤
                    │ 2. Has a spec?  spec engine              │  1,249 routes
                    │    src/components/workspace/spec/        │
                    ├──────────────────────────────────────────┤
                    │ 3. Otherwise    dataset engine           │  560 routes
                    │    src/components/workspace/engine/      │
                    └──────────────────────────────────────────┘
```

**1 — Flagship surfaces** are written by hand because the generated one could not say what the screen needs to say:

| Route | Surface |
|---|---|
| `sales-order/order-book` | Filterable, sortable order book |
| `inventory-store/stock-summary` | Stock position by type, age and location |
| `qms/quality-dashboard` | Rejection / rework / first-pass-yield trends |
| `finance-accounts/financial-overview` | Cash, receivables, P&L roll-up |
| `proforma-invoice/print-preview-export` | **PI Studio** — full document editor with live A4 preview |

**2 — The spec engine** reads a `WorkspaceSpec` (plain data: what one row *is*, which fields it carries, which statuses it can hold) and produces a working ERP surface: seeded records, KPI band, faceted filters, search, full CRUD, a kanban board, a month schedule, an analytics panel, a settings panel, CSV export, and — for Proforma Invoice — a printable document.

**3 — The dataset engine** covers submodules that have not been given a spec yet. It picks a dataset from the registry binding (or falls back to one that suits the module's business group) and generates the same view set from it, so a screen always reads like the domain it lives in.

### The workspace spec DSL

A spec is authored as compact strings — `key|Label|kind|args` — parsed by [`src/lib/workspaces/dsl.ts`](src/lib/workspaces/dsl.ts):

```ts
export const QMS: ModuleSpecs = {
  "capa-register": {
    name: "CAPA Register",
    kind: "list",
    summary: "Corrective and preventive actions",
    entity: "CAPA",
    ref: "CAPA",
    fields: [
      "capaNo|CAPA No|code",
      "buyer|Buyer|enum|@buyers",          // named pool
      "owner|Owner|person",                 // renders with an avatar
      "qty|Affected Qty|int|500;40000;pcs",
      "yield|First Pass Yield|pct",         // renders as a meter
      "due|Target Date|date|-20;60",        // days from today
      "value|Cost Impact|money",
    ],
    statuses: ["Open", "In Progress", "Verified", "Closed"],  // most common first
    measure: "value",
    insight: "Three CAPAs are past their target date.",
  },
  // …
};
```

Field kinds: `code` · `text` · `enum` · `person` · `int` · `money` · `pct` · `float` · `date` · `bool` · `status`. Pools `@people`, `@buyers`, `@suppliers`, `@items` supply realistic vocabulary.

**Navigation is derived from the spec, not declared twice.** [`submodulesOf()`](src/lib/workspaces/catalog.ts#L112) builds the registry entries from the same object the engine reads, so a workspace can never exist without a menu item, or a menu item without a workspace.

### Data generation and persistence

- **[`src/lib/data/rng.ts`](src/lib/data/rng.ts)** — a seeded PRNG. Every row is a pure function of its route key, so the server render and the client hydration produce byte-identical output, and a reprinted document always matches the copy already in the buyer's hands.
- **[`src/lib/workspaces/record-store.ts`](src/lib/workspaces/record-store.ts)** — `localStorage` *is* the database in this build. One store per workspace route, keyed `metal-erp:records:<module>/<submodule>`. It exposes two snapshots — the seeded rows for the server render, the persisted rows for every render after — and `useSyncExternalStore` picks the right one, which is why hydration never flashes. Rows carry a field/status **signature**; a spec change invalidates stale rows instead of rendering empty columns. A write in another tab invalidates the snapshot via the `storage` event.

Other browser-persisted keys: `smart-erp-theme`, `smart-erp-sidebar-collapsed`, `smart-erp:pi-studio-draft`.

## Feature tour

### CEO Command Center (`/dashboard`)

A single scrolling briefing — 12 labelled sections carrying 20 titled cards: headline KPI band, business performance, revenue composition, cash position and a 13-week rolling cash-flow forecast, sales by country, product-family mix, order pipeline and top buyers, line OEE, machine capacity heatmap, production flow, quality trend and defect Pareto, inventory composition and stock aging, supplier capability radar, order-value-vs-margin scatter, energy consumption, shipment status — plus live alerts, AI insights, system status, approvals and quick-action panels.

Every chart card ships a **table-view twin** (the same numbers, reachable without reading the chart), a legend when it carries multiple series, and a period filter that re-scopes the surface. The E2E suite asserts all of that, plus that the page body never scrolls horizontally and renders without console errors.

### Workspaces

Each workspace exposes the views that suit its kind, and opens on the right one:

| Kind | Opens on | Also available |
|---|---|---|
| `overview` / `analytics` | Analytics | Records, Board, Schedule, Settings |
| `list` | Records | Board, Schedule, Analytics, Settings |
| `board` | Board (kanban by status, drag between columns) | Records, Analytics |
| `calendar` | Schedule (month grid, navigable) | Records, Analytics |
| `form` | Entry form | Records, Analytics |
| `settings` | Configuration switches | Records, Analytics |

Across all of them: a derived KPI band that reacts to your edits, full-text search, faceted filters, column sort, row selection, create/edit/delete with required-field validation, a record detail drawer, CSV export (formula-injection safe), toast feedback, and a reset that discards local changes and restores the seeded dataset.

### PI Studio (`/m/proforma-invoice/print-preview-export`)

The flagship document surface. The register can only print what a stored record holds; the studio is for the PI that has to say something the register cannot express — a second item, a re-worded clause, a buyer's house colour, a bank copy with the marks stripped off.

- Panelled editor over every field: parties, terms, goods (size-broken line tables), money, clauses, document design
- Live A4 preview beside it, redrawing as you type, with 50 %–150 % zoom
- Templates that restyle the sheet and drop the blocks a given recipient does not need
- Six accent palettes, copy labels and watermarks
- Totals re-derive whenever a size row changes
- Explicit **Save** to a `localStorage` draft — never silent, so the studio always opens on a document you recognise
- Print straight to the browser dialog, where *Save as PDF* produces the file

Supporting libraries: [`src/lib/pi/document.ts`](src/lib/pi/document.ts) (company profile, bank block, 11 standard conditions, document checklist, deterministic document assembly) and [`src/lib/pi/options.ts`](src/lib/pi/options.ts) (templates, palettes, tinting).

### Command palette

`⌘K` / `Ctrl+K` opens a search across all ~1,884 modules and submodules. Ranking is exact-match → prefix → word-start → substring → context, with top-level modules winning ties. Escape closes; empty results report cleanly rather than crashing.

### Codes

Pure-TypeScript **Code 128-B** barcode and **QR** encoders ([`src/lib/codes/`](src/lib/codes/)) render document references as inline SVG rectangles — no runtime dependency, no external requests, CSP-safe.

## Design system

[`src/app/globals.css`](src/app/globals.css) is the single token layer. **Dark-first**: the server renders `data-theme="dark"` and the theme provider reconciles with the stored preference after mount — read during render via `useSyncExternalStore`, so there is no second render pass and no inline bootstrap script (which is what keeps `script-src` free of an extra hole).

- **Surfaces** — `--bg-base`, `--bg-sunken`, `--bg-surface`, `--bg-surface-2/3`, `--bg-overlay`
- **Ink** — primary / secondary / muted / inverse, all clearing WCAG 4.5:1
- **Status** — good, warning, serious, critical, info, neutral (each with a soft variant). Reserved: never used as a series colour.
- **Categorical series** — 8 fixed slots, never cycled, validated for CVD safety, lightness, chroma and 3:1 contrast against the real chart surfaces in *both* themes
- **Sequential ramp** — single hue, light → dark

Themes swap by overriding variables under `[data-theme="light"]`. There are no `dark:` variants anywhere in the component layer.

Component library: cards, badges, buttons, data tables, tabs and segmented controls, modals and drawers, confirm dialogs, toasts, form controls (text, select, textarea, switch, slider, filter), stat tiles, progress rings/bars/stacked meters, sparklines and micro-bars, skeletons, avatars, empty states. Charts: trend area, multi-line, series bar, combo bar-line, donut, radial gauge, radar, funnel, heatmap, scatter, ranked bars.

## Security posture

For a build with no backend, the attack surface is the browser — and it is deliberately narrowed.

**Response headers** ([`next.config.ts`](next.config.ts)) on every route:

- `Content-Security-Policy` — `default-src 'self'`, `object-src 'none'`, `frame-ancestors 'none'`, `frame-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `connect-src 'self'` (no off-origin egress at all), `upgrade-insecure-requests`. `'unsafe-eval'` is development-only.
- `Permissions-Policy` denying 16 capabilities the ERP never uses — camera, microphone, geolocation, USB, payment, WebAuthn, screen capture and more
- `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`
- `Cross-Origin-Opener-Policy` / `Cross-Origin-Resource-Policy: same-origin`, `Origin-Agent-Cluster: ?1`
- `Strict-Transport-Security` with a two-year max-age, `X-Robots-Tag: noindex, nofollow`, and `poweredByHeader: false`

**Input handling** ([`src/lib/security/sanitize.ts`](src/lib/security/sanitize.ts)) guards the places where a value stops being text and becomes something else — a URL, a route segment, a style value, a CSV cell:

| Helper | Guards against |
|---|---|
| `parseSlug` / `isValidSlug` | Path traversal, encoded traversal, absolute URLs, null bytes — rejected, not escaped |
| `sanitizeQuery` | Control and invisible characters (zero-width, bidi overrides), length-capped at 120 |
| `isSafeInternalPath` / `safeInternalPath` | Open redirects: `//evil.com`, `javascript:`, backslash normalisation |
| `safeCsvCell` | Excel/Sheets formula injection (`=`, `+`, `-`, `@`, tab, CR) |
| `safeColor` | Data-driven colours smuggling `url(...)` or arbitrary CSS into inline styles |
| `escapeHtml`, `safeNumber` | Non-React markup contexts; unbounded numeric input |

Character classes are written as numeric code-point checks rather than regex literals — a literal containing raw control bytes is invisible in a diff.

**Codebase invariants**, enforced by [`tests/security/source-audit.spec.ts`](tests/security/source-audit.spec.ts): `dangerouslySetInnerHTML` is never used, anywhere. The audit also guards itself against vacuous passes by asserting it actually scanned files.

## Extending the system

### Add a submodule to a spec-driven module

Open the module's file in [`src/lib/workspaces/specs/`](src/lib/workspaces/specs/) and add one keyed entry. That is the whole change — navigation, the workspace, the route and the prerendered page all follow from it:

```ts
"tool-life-log": {
  name: "Tool Life Log",
  kind: "list",
  summary: "Strokes and wear per die",
  entity: "Tool Life Record",
  ref: "TLL",
  fields: [
    "logNo|Log No|code",
    "die|Die|enum|D-101;D-102;D-203",
    "strokes|Strokes|int|1000;500000",
    "wear|Wear|pct",
    "checkedBy|Checked By|person",
    "checkedOn|Checked On|date|-30;0",
  ],
  statuses: ["Within Limit", "Watch", "Replace"],
  rows: 48,
  measure: "strokes",
},
```

### Add a whole module

1. Write `src/lib/workspaces/specs/<slug>.ts` exporting a `ModuleSpecs` object.
2. Register it in [`src/lib/workspaces/catalog.ts`](src/lib/workspaces/catalog.ts) under `WORKSPACE_SPECS`.
3. Add the `ErpModule` entry in [`src/lib/modules/registry.ts`](src/lib/modules/registry.ts) with `submodules: submodulesOf(WORKSPACE_SPECS["<slug>"])`, an `icon` (any lucide name), a `group` and a `tone` (1–8).

### Promote a workspace to a flagship surface

Build the component under [`src/components/workspace/flagship/`](src/components/workspace/flagship/), then add its `"module/submodule"` key to both `FLAGSHIP_ROUTES` and the dispatch switch in [`flagship/index.tsx`](src/components/workspace/flagship/index.tsx). Dispatch is a switch returning JSX rather than a lookup returning a component *type* — selecting a component reference during render would reset its state if the reference ever changed identity.

### House rules

- The module registry is **plain data with no React imports** — icons are string keys resolved by `<ModuleIcon />`, so the registry crosses the Server/Client boundary freely.
- Never hand-write a submodule entry for a spec-driven module; derive it.
- Never reach for `dangerouslySetInnerHTML`; the test suite fails the build.
- Colour comes from tokens, never from literals in components.

## Known gaps and roadmap

Honest list of what is unfinished:

- **No backend.** Auth, persistence and authorization all live in the browser. This is the single largest piece of work between here and production.
- **Unwired specs.** `src/lib/workspaces/specs/mes.ts`, `production.ts` and `wip.ts` (20 workspaces each) are written but not registered in `WORKSPACE_SPECS`, so they do not render.
- **A dead flagship route.** `mes/shop-floor` is listed in `FLAGSHIP_ROUTES`, but no module with slug `mes` exists in the registry, so `ShopFloorWorkspace` is unreachable.
- **CSP `'unsafe-inline'`.** Unavoidable while every page is statically prerendered; resolve it with a per-request nonce in `proxy.ts` once pages go dynamic.
- **Login is client-side.** Credentials are compared in the browser against a constant — replace before any deployment that is reachable from outside a trusted network.
